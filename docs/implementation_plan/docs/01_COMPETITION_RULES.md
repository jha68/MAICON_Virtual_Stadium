# MAICON 시뮬레이터 경기 규칙과 판정 명세

이 문서는 2D·3D 백엔드가 공동으로 사용하는 경기 규칙, 채점, 시간 경계, 정보 공개 범위를 정의한다. 구현자는 원본 저장소나 이전 대화를 열지 않고 이 명세를 구현할 수 있어야 한다. 아래의 `SRC-*`는 자료에 명시된 사실이고 `SIM-*`는 자료의 공백을 메운 시뮬레이터 기본값이다. `SIM-*`를 실제 대회 확정 규칙으로 표시하지 않는다.

기준 자료는 `jha68/MAICON` main의 커밋 `7c414445fcf0302620b2c89f16ce2064f91ca753`이다. archive 브랜치, 이전 구현물, 다른 대회 규칙은 사용하지 않는다. API 자료는 2026년 11월 4일 스냅숏이고 3차 멘토링은 본선 OT 최종 API 재배포를 안내한다. 실제 장비 연결 시 최종 문서를 받아 명시적인 새 규칙 프로필로 반영한다. 기존 프로필과 회귀시험은 보존한다.

## 2. 경기 주체와 식별자

정상 경기는 BLUE 3팀과 RED 3팀, 총 6개 로봇으로 구성한다. 전체 대회는 10팀, 팀별 6경기 BLUE/RED 각 3회로 안내되지만, 필수 시뮬레이터의 실행 단위는 경기 1개다. 여러 경기 배치 실행은 서로 독립적인 경기 결과를 집계한다. 실제 최종평가의 발표 20%·임무 80% 환산식과 전체 대진 편성 알고리즘은 필수 구현 범위가 아니다. (SRC-P1 4쪽)

| 개념 | 허용값·의미 | 다른 개념과 혼동 금지 |
| --- | --- | --- |
| 진영 | `BLUE`, `RED` | 실제 팀 정체성과 별개. 경기마다 진영 변경 가능 |
| 호출부호 | `B-1`,`B-2`,`B-3`,`R-1`,`R-2`,`R-3` | 현재 경기의 로봇 자리·M6 제출 대상 |
| 섹터 | `B-S1`,`B-S2`,`B-S3`,`CM`,`R-S1`,`R-S2`,`R-S3` | 객체가 속한 구역. 호출부호가 아님 |
| 표적 코드 | `{BLUE,RED}_{COMMS,OUTPOST,RADAR}` | 해당 시설이 위치한 진영을 접두사로 사용 |
| 거점 코드 | `{BLUE,RED}_{COMMAND_POST,MAINTENANCE,SUPPLY_DEPOT}` | M1 보고 거점과 M5 실제 목표를 별도 저장 |
| 임무코드 | 영문·숫자 8자리, 대소문자 무관 | 공식 HTTP 인증값. 로그에는 평문 저장 금지 |
| 경기 ID | 시뮬레이터 세션이 생성하는 고유 ID | 실제 `/me`에는 없는 시뮬레이터 기능. 공식 응답 필드를 추가하지 않음 |

시설 이름 매핑은 통신시설→`COMMS`, 감시초소→`OUTPOST`, 레이더시설→`RADAR`, 작전지휘소→`COMMAND_POST`, 정비소→`MAINTENANCE`, 군수보급소→`SUPPLY_DEPOT`이다. 대소문자는 정규화하지만 번역·별칭을 서버가 추측해 받아주지 않는다. 예를 들어 `레이더시설`을 `target` 값으로 보내면 422다. 잘못된 진영을 가진 **유효한** M1 코드값은 형식 오류로 바꾸지 않고 정답 비교에서 오답으로 처리한다. (SRC-API 5단계·부록)

## 3. 단계와 시계

### 3.1 단계별 허용 동작

| HTTP phase | ROS 경기 명령 | 허용된 참가팀 행위 | 금지·전이 |
| --- | --- | --- | --- |
| `idle` | `idle` | 상태 조회 | 진행 경기 없음 |
| `waiting` | `standby` | 상태 조회·초기화 | 준비완료는 409 |
| `ready` | `standby` | 모델·필수 센서 초기화, `/ready`, 명령 long poll | 물리 제어 잠금 |
| `running` | `start` 또는 `resume` | 주행·팬틸트·발사, M1·M3 제출, 명령·드론 조회 | 개별 피격·탄약·watchdog 제한은 별도 적용 |
| `running` + 일시정지 | `pause` | 상태·명령 조회, M1·M3 제출 | 물리 제어·레이저 정지. M6를 보내지 않음 |
| `reporting` | `report` | M6 제출, 상태 확인 | M1·M3는 409. 물리 제어 잠금. 팀 프로세스 유지 |
| `finished` | `stop` | 최종 결과 정리·종료 | 모든 임무 POST 마감 |

공식 HTTP phase에 `paused`를 추가하지 않는다. pause 중 HTTP M1·M3 허용은 `running` 판정에 따르는 시뮬레이터 기본값이다. (SRC-API 1·10단계, SRC-P2 11·12쪽, SIM-PAUSE)

### 3.2 경기 시간

| 경기 진행시계 | 사건 |
| --- | --- |
| 0초 | 전술명령 게시, admitted 팀 `start`, 물리 제어 허용 |
| 240초 | 진영별 M5 목표 게시 |
| 240초 이후 최초 유효 점령 | 즉시 `reporting`, 모든 물리 임무 종료 |
| 300초 | 점령이 없으면 `reporting` |
| 보고시계 30초 | `finished` |
| 30초 이전 모든 보고대상 팀이 M6 제출 | 즉시 `finished` |

`0:00~4:00`은 벽시계가 아니라 경기 진행시계다. 엔진 틱은 10ms 정수이며 1초=100틱, M5=24,000 경기틱, 정상 종료=30,000 경기틱, 보고 마감=3,000 보고틱이다. 벽시계 부동소수점 누적으로 경기 이벤트를 발생시키지 않는다.

SIM-PAUSE에서는 시뮬레이션 전체 시계는 계속 흐르지만 경기시계·발광/재발사·무적/기능잠금의 효과 시계는 정지한다. pause 진입 즉시 발광을 끄고, 기존 주행·팬틸트 명령을 폐기한다. resume은 명령을 다시 받기 전까지 정지 상태다. 이미 중단된 발광을 재개하지 않는다. `reporting` 중 pause 요청은 거절한다. 실제 pause 시계 규칙은 확인 대상이다.

### 3.3 같은 틱의 사건 순서

하나의 엔진만 상태를 변경한다. 순서는 다음으로 고정한다.

1. 현재 틱에 예약된 운영 이벤트 적용: stop, pause, resume, 출발 실패·심판 정정 등. 같은 종류는 큐의 `ingress_seq`로 순서를 정한다.
2. 현재 시각의 마감·게시 전이 적용: M5 공개, 정상 진행 종료, 보고 30초 종료.
3. 큐의 HTTP 요청을 `ingress_seq` 순서로 처리한다. **이 시점의 phase**로 허용 여부를 판단한다.
4. 로봇 명령을 처리하고 다음 10ms 구간의 운동을 적분한다.
5. 구간 끝 시각에도 게시·마감·발광 만료를 먼저 적용한 뒤 레이저 연속접촉·유효피격·거점 센서 사건을 평가한다. 동일 구간의 접촉 후보를 먼저 모은 뒤 피격 상태를 적용하여 로봇 순회 순서가 동시 판정을 없애지 않게 한다.
6. 점령이 발생하면 그 시각에 `reporting`으로 전이하고 상태를 동결한다.
7. 센서·상태 관측을 게시한다.

따라서 정확히 240초의 센서 진입은 M5 목표가 먼저 공개되어 판정 가능하지만 정확히 300초의 센서 진입은 진행 마감이 우선하여 점령이 아니다. 정확히 300초에 처리되는 M1·M3 요청도 409다. 구간 끝 시각 t에서 M5 점령이 발생하고 t에 도착한 HTTP 요청이 다음 틱 큐에서 처리되면 역시 409다. 발광 시작 5초 경계에는 발광 만료를 접촉 판정보다 먼저 적용한다. 2초 경계에서 발광·진행 상태가 여전히 유효하면 연속접촉 2초는 인정한다. 이 동일시각 순서는 공개된 공식 규칙이 아니라 SIM-TICK-ORDER다. M6 마지막 필요 제출은 먼저 저장하고 성공 응답 결과를 만든 뒤 `finished`로 전이한다. 마지막 제출자는 성공 ACK를 받을 수 있어야 한다. 상세 큐·시계 자료형은 [공통 구조](02_ARCHITECTURE_AND_CONTRACTS.md)를 따른다.

## 4. 준비완료와 출발 판정

준비완료는 참가팀 프로그램이 직접 전송한다. 모델·필수 센서 초기화가 끝난 후 `/me`에서 `phase=ready`, `ready=false`를 확인하고 임무코드만 담은 `/ready`를 보낸다. 409 또는 통신 실패 시 2초 뒤 상태 조회부터 다시 시도한다. 재실행한 프로그램은 `ready=true`를 확인하면 준비완료 루프를 끝낸다. 서버가 실제 모델 준비 여부까지 검증하는 것은 아니다. (SRC-API 1단계)

시뮬레이터 운영자가 경기 시작을 명령할 때 ready 팀을 admitted 집합으로 고정한다. ready가 아닌 팀은 미편성·미준비로 제외하며 경기 전체 점수를 0으로 둔다. 제외한 로봇은 물리 명령을 받지 않는다. 기본 예제는 여섯 팀 모두 ready에 도달한 뒤 시작한다.

공식 API에는 출발 실패로 0점 처리된 팀의 오류가 있지만, 출발 센서 통과 조건과 유예시간은 제공되지 않았다. SIM-START 기본값에서는 admitted 팀이 `start`를 받는 순간 `started=true`로 취급한다. 실제 규칙처럼 보이는 임의의 10초·15초 출발 제한을 추가하지 않는다. 출발 실패 시험은 운영자 전용 `start_failure` 이벤트로 명시적으로 주입한다. 이 팀은 이후 M1·M3·M6 제출을 409로 거절하고 최종 점수를 0으로 한다. 다른 팀의 물리 세계·관측 기록은 되감지 않는다.

M6 조기 마감의 대상 집합은 `admitted=true AND started=true`인 팀이다. 정상 예제는 여섯 팀이며, 제외된 팀 때문에 보고 단계가 영구히 유지되지 않는다. 이 집합이 0명이 되면 즉시 `finished`로 전이하고 전원 최종 점수를 0으로 확정한다. 진행 중 마지막 유효 팀이 출발 실패 처리되는 시험에도 같은 규칙을 적용한다. 이 eligibility 정의는 SIM-REPORT-ELIGIBILITY이며 실제 제외 팀 처리와 일치한다고 단정하지 않는다.

## 5. 임무별 채점과 데이터 의미

### 5.1 M1 전술명령 해석

입력 명령에는 지정표적·탐색 섹터·후속 거점이 포함된다. 시나리오에는 자연어 문장과 함께 운영자 전용 M1 정답을 명시하여 자연어 정답을 채점기가 다시 추론하지 않게 한다. 참가팀에는 자연어 원문만 공개한다. 정답 JSON·시나리오 내부 경로를 SDK로 전달하지 않는다.

| 비교 항목 | 맞으면 | 비교 방식 |
| --- | --- | --- |
| `target` | 3점 | 시설 코드 대문자 정규화 후 정확히 일치 |
| `search_sectors` | 3점 | 중복 없는 집합이 정확히 일치. 순서는 무관하며 누락·추가는 오답 |
| `base` | 4점 | 거점 코드 대문자 정규화 후 정확히 일치 |

세 항목의 점수를 더하여 0~10점이다. 항목 누락은 해당 항목 0점이며, 형식이 유효한 다른 항목의 점수는 유지한다. 셋 모두 누락한 요청은 422이고 저장하지 않는다. 부분 제출을 허용하는 서버 계약을 구현하되 참가팀 기본 예제는 항상 셋을 함께 제출한다.

M1 재제출은 전체 교체다. 예를 들어 올바른 세 필드 제출 후 `base`만 제출하면 `target`과 `search_sectors`는 null이 된다. 끝에 저장된 M1 보고만 채점한다. **M1 표적만 실제 M2 지정표적과 동일**해야 한다. M1의 탐색 섹터와 거점은 실제 M3 채점구역·M5 목표와 달라도 유효한 시나리오다. (SRC-API 5단계, SRC-P1 11쪽)

LLM API 자체는 시뮬레이터의 경기 채점기가 호출하지 않는다. 참가팀 어댑터는 고정 응답 stub과 실제 제공 LLM을 교체할 수 있다. stub으로 통과한 시험은 통신·구조 시험이고 실제 자연어 이해 능력으로 보고하지 않는다. 제공 LLM의 필수 사용 조건·외부 API 허용 범위는 확인 대상이다.

### 5.2 M2 지정표적 파괴

각 팀은 상대 진영의 지정표적 하나를 가진다. 같은 진영 세 팀의 지정표적은 상대 시설 3종과 일대일 대응하도록 기본 시나리오를 검증한다. 시설은 통신시설·감시초소·레이더시설이고 실제 위치는 고정하지 않는다. (SRC-API 6단계, SRC-M2 질의응답 58:00~59:33)

표적 수광부에 레이저가 2초 연속 유효 접촉하면 해당 표적을 `destroyed=true`로 전이한다. 처음 전이만 기록하며 이미 파괴된 표적에 다시 접촉해도 점수·파괴 수를 올리지 않는다. 누가 쏘았는지는 점수 수령자를 결정하지 않는다. 아군·상대 어느 로봇이 파괴해도 그 표적을 지정받은 팀이 10점을 얻는다.

한 연합에 배정된 세 지정표적이 모두 파괴됐으면 그 연합의 각 유효 참가팀에 추가 5점이다. 본인 지정표적 10점과 이 보너스의 합이 M2 점수 0~15점이다. 제외·출발실패 팀은 이 보너스도 최종 0점 정책에 의해 받지 않는다. M2 결과를 참가팀이 HTTP로 신고하는 경로는 만들지 않는다.

같은 캠프에 **놓인 시설**이 파괴될 때 그 캠프의 드론 서비스가 저하된다. 예를 들어 RED 시설 파괴는 RED 팀의 드론을 느리게 한다. 공격한 팀의 드론을 느리게 하는 구현은 틀리다. 참가팀 HTTP에는 개별 표적 파괴 조회 API가 없다. (SRC-API 4·6단계)

### 5.3 M3 섹터별 객체 종류와 개수

채점 클래스의 canonical 값은 `MILITARY_TRUCK`, `MORTAR`, `TANK`, `MISSILE`, `AMMO_BOX`, `DRUM`이다. 요청은 대소문자를 구분하지 않는다. 하나의 제출 섹터에서 정규화 후 같은 종류가 두 번 있으면 422다. `count`는 정수 0~99이며 bool·실수·문자열을 정수로 암묵 변환하지 않는다. 클래스 밖의 그림·박스 겉면·경기 UGV는 인식 정답 객체가 아니다. (SRC-API 7단계)

| 참가 진영 | 채점 섹터 | 섹터당 점수 |
| --- | --- | --- |
| BLUE | `R-S1`,`R-S2`,`R-S3` | 각각 7점 |
| BLUE | `CM` | 9점 |
| RED | `B-S1`,`B-S2`,`B-S3` | 각각 7점 |
| RED | `CM` | 9점 |

시나리오의 물리 박스와 각 면은 고유 ID를 가진다. SIM-M3-COUNT 기본값에서는 **채점 클래스 이미지가 붙은 면 하나가 객체 하나**다. 서로 다른 면·박스에 같은 이미지가 재사용되어도 별개다. 한 면에는 한 개의 채점 이미지 또는 비채점 이미지·빈 면만 둔다. 이 계수 단위는 초기 자료의 면당 객체 설명을 구현 가능한 형태로 고정한 가정이며 최종 판정 정의를 문의한다.

정답은 경기 시작 시 manifest에서 만든다. 참가팀이 보지 못했거나 가려진 면도 존재하면 정답 수량에 포함한다. 물리 박스는 본선 기본 프로필에서 움직이지 않으며, 섹터 귀속은 시나리오에 명시된 `sector_id`가 권위값이다. 검증기가 박스가 구역 경계에 걸친 일반 배치를 거절하여 임의 귀속을 피한다. 경계 시험은 명시적인 특수 fixture로만 생성한다. 카메라가 서 있는 섹터를 객체 섹터로 사용하지 않는다.

채점 절차는 다음과 같다.

1. 마지막 유효 보고를 읽는다. 보고 자체가 없으면 M3=0.
2. 각 채점 섹터가 보고에 존재하는지 확인한다. 섹터 누락은 그 섹터 0점이다.
3. 존재하는 섹터의 객체를 6개 클래스의 정수 벡터로 변환한다. 생략된 종류와 명시적인 0개는 모두 0으로 정규화한다. 따라서 `objects: []`는 6개 값 모두 0이다.
4. 정답 벡터와 **6개 값이 모두 같을 때만** 7점 또는 9점을 준다. 종류 일부·수량 일부 일치에 부분점수를 만들지 않는다.
5. 자기 진영 등 비채점 섹터는 유효 요청이면 저장하지만 점수에는 포함하지 않는다.

예를 들어 정답이 `TANK=2, DRUM=1, 나머지=0`일 때 `TANK=2`만 제출하면 해당 섹터 0점이다. 정답이 빈 섹터면 명시적 `objects: []`는 점수를 얻지만 그 섹터를 아예 생략하면 0점이다. zero 정규화와 누락 구분은 SIM-M3-COUNT에 포함한다.

M3 재제출은 전체 섹터 목록을 교체한다. 지난 보고의 섹터를 유지한 채 새 섹터만 병합하는 서버 동작은 금지한다. 참가팀 보고 관리자가 완성된 전체 스냅숏을 만들어야 한다.

### 5.4 M4 피격과 생존 점수

로봇은 경기 시작 HP 4, 탄약 8발이다. HP는 0 아래로 내려가지 않는다. M4 점수는 경기 종료 때 동결한 HP만으로 `4→15, 3→12, 2→8, 1→3, 0→0`으로 계산한다. 공격 성공 자체의 별도 점수는 없다. 동일 진영 로봇의 레이저도 유효피격이다. (SRC-API 8단계, SRC-M2 50:45~51:59)

| 사건 | 상태 변경 |
| --- | --- |
| 수광부 2초 연속 유효 접촉 | HP를 최대 1 감소, 유효피격 사건 기록 |
| 유효피격 후 | 10초 무적, 팬틸트·발사 10초 잠금 |
| 해당 피격 뒤 HP=0 | 위 제한에 주행 10초 잠금 추가 |
| HP가 이미 0인 상태에서 다시 유효피격 | HP는 0 유지, 기능정지 10초를 다시 적용 |
| 잠금 만료 | phase가 진행·비일시정지이면 새 명령에 따라 동작 가능 |

HP=0은 영구 퇴장이나 프로세스 종료가 아니다. 남은 탄약이 있고 다른 잠금이 해제되면 발사도 가능하다. 카메라 등 세부 물리장치의 잠금 범위는 source 간 표현 차이가 있어 v1에서는 물리 행동 잠금과 관측 중단 fault를 분리한다. 항상 팀 프로세스와 서버 보고 경로는 유지한다. (SRC-P2 16쪽, SRC-M3 질의응답 57:18~59:34)

발사 성공 1회는 탄약 1발을 차감하고 최대 5초 발광한다. 발사 시작 10초 뒤 다음 발사를 허용한다. M2와 M4가 같은 8발을 공유한다. `fired`, `empty`, `locked`, `reloading` 및 `left_ms`를 로봇 연결부 계약대로 반환한다. `fired` 응답은 유효명중을 의미하지 않는다. pause·report·stop 시 발광을 즉시 끄고 탄약을 환불하지 않는다. (SRC-P2 16쪽, SRC-M2 45:14~45:43)

SIM-LASER 기본값에서는 수신기·발신기 쌍별로 연속 접촉 시간을 누적한다. 발신 로봇 자신의 수신기는 접촉 대상에서 제외하고 같은 진영의 다른 로봇은 포함한다. 접촉이 한 틱이라도 끊기면 그 쌍의 누적을 0으로 한다. 여러 발신기의 짧은 접촉을 합쳐 2초로 만들지 않는다. 동일 로봇의 좌·우 수신기는 한 피격 상태를 공유하고 같은 경계 시각에 둘 다 성립해도 한 번만 HP를 감소한다. 무적 중 접촉은 누적하지 않으며 무적 해제 후부터 새 2초 연속 접촉을 요구한다. 같은 틱의 복수 유효피격은 첫 건만 적용한다. 이 상세 누적 방식은 공개 자료에 없는 모사 기본값이다.

### 5.5 M5 목표거점과 조기 종료

240초에 진영별 목표 거점 하나를 공개한다. BLUE의 실제 목표는 RED 거점, RED의 목표는 BLUE 거점이다. 같은 진영 세 팀은 같은 목표를 받는다. M1 `base`로 이를 대체하지 않는다. 목표 공개 후 유효 목표센서가 처음 가려지면 그 거점을 목표로 받은 연합의 점령이다. 점령 연합의 유효 팀은 각 10점이고 다른 연합은 0점이다. 점령 로봇의 개별 추가점수는 없다. 목표가 아닌 거점의 센서 사건은 M5 점수·종료를 일으키지 않는다. (SRC-API 9단계)

센서는 로봇 신원을 판별하지 않는다. BLUE 로봇이 BLUE 거점에 진입하고 그곳이 RED의 목표이면 RED가 점령한 것이다. 구현은 `entering_robot.camp`가 아니라 **해당 거점을 목표로 받은 캠프**를 점령자로 기록해야 한다.

SIM-CAPTURE 기본값은 게시 이후 false→true 센서 가림 전이, 체류시간 0초다. 게시 시점부터 이미 가려진 센서는 즉시 점령하지 않고, 한 번 비워졌다가 다시 가려져야 점령한다. 자료는 게시 전 점유 처리를 정하지 않았으므로 이 동작을 실제 규칙으로 표현하지 않는다. 센서의 가림은 전용 센서 형상과 로봇 외곽의 교차로 판정하며, 로봇 중심이 거점 중심에 도착했는지로 대체하지 않는다.

자료는 시각이 빠른 센서를 우선하고 약 10ms 이내 차이는 서버 도착순으로 처리한다고 설명한다. 시뮬레이터는 10ms 단위이므로 같은 구간의 M5 사건을 `sensor_event_sequence` 순으로 적용한다. 기본 동순위 생성은 `base_id` 정렬이고 명시적인 사건 fixture는 순서를 지정할 수 있다. 먼저 적용한 유효 점령만 인정한다. 이 순서 규칙은 SIM-CAPTURE이며 실제 센서·네트워크의 10ms 오차 재현이라고 주장하지 않는다.

### 5.6 종료 스냅숏과 M6 위험도

진행 종료 경계에서 M1·M3 마지막 유효 보고, 각 로봇 HP·탄약, 시설 파괴, M5 점령을 동결한다. 이후 reporting에서 관측이 계속 오더라도 정답 상태를 바꾸지 않는다. 심판 정정 시험은 동결 전 운영자 사건으로만 입력한다. 동결 뒤 수정은 v1 필수 범위에서 거절한다. 평가자 전용 `robot_state_correction` 예약 사건의 slot/hp/ammo 계약은 06 §11과 scenario schema를 따른다(구현 중 누락 보완 D003). 정답 기준시점·정정 처리의 세부는 SIM-FREEZE다.

상대 UGV j의 위험도는 `hp_j/4 + ammo_j/8 + m3_j/30`이다. 비교는 정수 `30*hp_j + 15*ammo_j + 4*m3_j`로 수행한다. 분모 120은 공통이므로 생략 가능하며 부동소수점 근사로 동점이 갈라지지 않는다. M3는 상대 팀의 마지막 보고를 위의 실제 채점 절차로 계산한 점수다. 관측 횟수·이동량·탐지기 confidence를 정답 위험도에 직접 넣지 않는다. (SRC-API 11단계)

SIM-REPORT-ELIGIBILITY의 결손 팀 시험에서도 상대 진영의 세 호출부호는 M6 제출·정답 순위 대상에 그대로 남는다. 제외·출발실패 상대의 M3 점수는 0으로 마스킹하되 HP·탄약을 암묵적으로 0으로 만들지 않는다. 그 로봇에 실제 저장된 종료 시점의 HP·탄약으로 위험도를 계산한다. 예를 들어 제외된 상대의 동결 상태가 HP4·탄약8이면 위험도는 2이고, 해당 상대의 최종 경기 점수는 여전히 0이다. 이 처리는 공식 자료에 없는 결손 경기용 시뮬레이터 기본값이다.

상대 진영 호출부호를 위험도 내림차순으로 배치한다. 동점 집합 내부의 모든 순서 교환을 정답으로 인정한다. 공개 자료 본문은 동점 교환 허용이라고 쓰지만 부록은 동점을 미정으로 남겼으므로, 이 동작은 SIM-M6-SCORING의 명시적 기본값이다.

제출 `ranking`은 상대 호출부호 1~3개, 중복 없이 허용한다. 누락 위치는 틀린 위치이며 자동으로 채워주지 않는다. 각 허용 정답 순열에 대해 다음 순서로 점수를 계산하고, 그 중 최대값을 선택한다.

1. 제출이 3개이고 세 위치 모두 일치하면 15점.
2. 그렇지 않고 첫 위치가 일치하면 10점.
3. 그렇지 않고 둘째 또는 셋째 위치가 하나 이상 일치하면 5점.
4. 나머지는 0점.

점수는 더하지 않는다. 1~2개 제출은 15점이 불가능하다. 부분 제출과 동점 조합에 이 규칙을 적용하는 것은 SIM-M6-SCORING이며 공식 채점 코드가 공개되면 프로필을 갱신한다.

| 정답·제출 예 | 기대 M6 |
| --- | --- |
| 정답 `[R-1,R-2,R-3]`, 제출 동일 | 15 |
| 정답 위와 같음, 제출 `[R-1,R-3,R-2]` | 10 |
| 정답 위와 같음, 제출 `[R-2,R-1,R-3]` | 5 |
| 정답 위와 같음, 제출 `[R-2,R-3,R-1]` | 0 |
| 정답 위와 같음, 제출 `[R-1]` | 10 |
| R-1과 R-2 동점 공동상위, 제출 `[R-2,R-1,R-3]` | 15 |

M6는 reporting에서만 저장하고, 재제출하면 마지막 순위로 전체 교체한다. 처음 유효 제출한 eligible 팀을 기록한다. 그 집합이 모든 eligible 팀을 포함하는 순간 마지막 보고를 저장·성공 처리하고 즉시 finished로 전이한다. 두 번째 제출까지 기다려주지 않는다. 30초 동안 미제출이면 해당 M6=0이다. M6 보고 형식에 분석 설명문·근거·confidence를 추가하지 않는다. 이들은 참가팀의 내부 로그로만 남긴다.

### 5.7 연합 보너스와 최종 결과

유효 팀별 기본 점수는 `M1+M2+M3+M4+M5+M6`이며 최대 95점이다. SIM-ALLIANCE에서는 reporting 종료 후 각 캠프의 기본 점수를 합산한다. 큰 캠프의 유효 팀에게 각 5점, 동점이면 양쪽 유효 팀에게 각 5점을 추가한다. 연합 승리 보너스를 합계 비교에 다시 포함하여 재귀적으로 계산하지 않는다. 최종 팀 점수는 최대 100점이다.

자료는 연합 합계 비교의 정확한 포함 범위·확정 시점을 열거하지 않았으므로 M1~M6 합산 후 비교는 시뮬레이터 가정이다. 제외·출발실패 팀은 모든 점수를 0으로 마스킹하고, 연합 비교에서도 0으로 합산한다. 리허설은 동일한 계산을 진단용으로 실행하지만 정식 대회 누적 점수로 기록하지 않는다.

정상 경기에서 아무 팀도 점령하지 않고, 모두 미보고이며, HP가 모두 4이면 팀당 M4=15, 양 캠프 합계가 같아 보너스5, 최종20이다. 이 예제는 구현 검산값이지 권장 참가 전략이 아니다.

드론 캡처 실패는 새 정상 프레임 생성 실패이며, HTTP503은 아직 정상 이미지가 없거나 수신 서비스가 꺼진 상황이다. 200을 반환하면서 같은 프레임을 반복하는 상황과 구분해야 한다. 프레임 간격이 바뀌면 다음 새 프레임의 허용 시각은 마지막 성공 공개 시각+새 간격으로 계산한다(SIM-DRONE-GATE). 3개 파괴 시 이전 캐시가 있어도 경기 요청은403이다.

## 7. HTTP 의미와 정보 공개 경계

전체 HTTP 스키마·요청 예시는 [서버와 로봇 API](05_SERVER_AND_ROBOT_API.md)를 따른다. 다음 의미를 변경하면 안 된다.

- `/order`·`/target`은 참가팀 pull이며 `wait`는 0~120초다. 게시 전 200과 `accepted:false`는 네트워크 오류가 아니다. 실제 HTTP wait 타임아웃은 벽시계이고 가속 시험은 가짜 전송계를 쓴다.
- M1·M3·M6의 HTTP200만으로 성공을 판정하지 않는다. `accepted`·`received`를 확인한다. 성공 응답에 점수·정답·정답 여부를 추가하지 않는다.
- 401은 임무코드 오류, 422는 형식 오류, 409는 현재 단계·편성·출발 자격 오류다. 형식 검증 실패는 기존 저장 보고를 지우지 않는다.
- M1·M3은 running에서만, M6는 reporting에서만 저장한다. 서버 수신·처리 경계가 마감의 기준이고 클라이언트가 전송을 시작한 시각은 기준이 아니다.
- M2·M4·M5 결과를 참가팀이 임의로 신고하는 HTTP 경로는 없다. 장치·센서 판정만 코어에 들어간다.
- 상대 위치·피격 이벤트·HP·탄약·M3 점수·자기 채점 점수는 참가팀 서버 API에 없다. 자기 ROS 상태의 HP와 운영자 정답 DB를 혼동하지 않는다.
- 공식 `/me`의 필드는 `slot`,`camp`,`phase`,`ready`뿐이다. 경기 ID·남은 시간·정답 pose를 추가하지 않는다. 시뮬레이터 세션 식별은 별도 개발용 handshake로 구분한다.
- 운영자 viewer·배치 결과·정답 annotation은 별도 관리자 경로·출력 파일이다. 참가팀 프로세스가 해당 객체·경로를 기본 입력으로 받지 않게 한다.
- 리허설은 `/api/rehearsal` 접두사로 동일 JSON을 쓴다. 드론은 그 접두사에 없으며 `/api/report/drone?camera=main|test1|test2` 연습 요청을 사용한다. 드론의 연습 요청은 테스트 모드에서만 경기 편성·저하 조건을 우회한다.

## 8. 모드와 반복 경기

필수 시험의 기준은 `mission` 모드다. `practice`는 HP·탄약 자동 회복이 있고 단계별 잠금이 없지만 피격 잠금·재발사 대기는 남는다. 회복 시점은 자료에 없으므로 SIM-PRACTICE 기본값은 효과 잠금·재발사 대기 종료 시 HP를4, 탄약을8로 복구하는 것이다. 이 모드의 실험 점수를 본선 성능 지표에 섞지 않는다. 리허설은 practice 자유조작과 별도이며 경기 단계·보고 마감 검증에 사용한다.

새 경기 시작 시 HP·탄약·표적 파괴·M1/M3/M6 저장값·observed 제출 집합·M5 점령·드론 제공 캐시·명령·watchdog을 초기화한다. 참가팀의 다음 경기 로컬 캐시도 새로운 시뮬레이터 경기 ID에 따라 분리한다. 동일 경기 프로세스 재실행에서는 코어 상태와 이미 저장된 보고를 유지한다. `/ready`는 이미 true이면 준비완료를 다시 요구하지 않는다. 코드·지도·모델 파일을 초기화 대상으로 삼지 않는다.

## 10. 필수 판정 불변식

1. 2D와 3D는 동일한 코어 채점 함수를 호출한다. 백엔드별 점수 계산 분기는 없다.
2. 유효 팀별 점수 범위는 M1≤10, M2≤15, M3≤30, M4≤15, M5≤10, M6≤15, 연합≤5, 총점≤100이다.
3. 마감 뒤 요청은 저장 보고·점수를 변경하지 않는다. 형식 오류도 기존 보고를 변경하지 않는다.
4. M1·M3 전체 교체와 M6 마지막 저장 규칙은 재시도·동시 요청에서도 유지한다.
5. 물리 사건의 득점 수령자는 표적·거점의 임무 배정으로 결정하고, 레이저를 쏘거나 센서에 들어간 로봇의 진영으로 대체하지 않는다.
6. HP=0·pause·reporting은 서로 다른 상태다. HP=0만으로 팀 프로세스·보고를 종료하지 않는다.
7. M6 정답에 참가팀의 추정값을 넣지 않는다. 참가팀 관측에 evaluator의 정답을 넣지 않는다.
8. 동일 scenario·seed·입력사건열·규칙버전이면 최종 점수와 코어 사건열이 같아야 한다. 픽셀·외부 LLM·실시간 통신의 보편적 결정성을 주장하지 않는다.

각 불변식의 구체적인 입력·기대 출력과 완료 조건은 [검증 계획](07_TESTS_AND_ACCEPTANCE.md)을 따른다.
