# Oracle 운영 서버 실측

2026-11-12 UTC. [실행 기록](https://github.com/jha68/MAICON_Virtual_Stadium/actions/runs/43230291498), [원시 수치](oracle-resources-43230291498.json).

운영 서버는 ARM64·CPU2개·RAM11.65GiB다. 운영 중인 것과 같은 이미지로 별도 컨테이너를 실행해 여섯 팀의 `baseline` 정책을60초간 측정했다. 경기 초기60초의 부하 측정이며 전체 임무 완료 시험은 아니다. 외부 LLM은 호출하지 않는 `FixtureLLM`을 사용했다. CPU 프로파일러는 사용하지 않고 약1초 간격으로 OS 자원 카운터를 수집했다.

기존 서비스는 종료된 경기 화면을 제공하는 상태로 유지했다. 테스트 컨테이너에는 CPU최대2개·RAM최대6GiB·낮은 CPU 우선순위를 지정하고 외부 네트워크·운영 자격 증명을 제공하지 않았다. 기존 경기 결과를 초기화하지 않았으며 테스트 전후 운영 경기 단계는 모두 `finished`였다.

| 항목 | 실측 |
|---|---:|
| 서버 전체 CPU 평균 |98.1%|
| 서버 전체 RAM 최대 사용 |1.80GiB /11.65GiB|

CPU 비율은 서버의 두 CPU 합계를100%로 표기했다. 테스트 실행60초의 자원 샘플과 준비·정리를 포함한 서버 전체74.7초의 측정 구간은 다르다. RAM 사용은 서버의 MemTotal−MemAvailable이며, 컨테이너 메모리 수치는 cgroup memory.current다. `movement_m`은 시작·종료 위치 간 직선 변위이며 누적 주행 거리가 아니다.

## 프로세스별 CPU

| 역할 | 평균 사용 코어 | 서버 전체 대비 |
|---|---:|---:|
| 여섯 참가팀 정책 합계 |0.895|44.8%|
| 카메라 렌더러 |0.241|12.1%|
| 경기 코어·API |0.207|10.4%|

테스트 중 서버 CPU는 포화에 가깝고 RAM은 여유가 있었다. 경기 시계 평균 속도는 정상이나 영상 생성 지연과 요청 누락이 컸다. 새 렌더링의 지연과 동일 장면 캐시를 포함한 전체 capture 지연은 다른 지표다. 같은 장면의 캐시 재사용은130회 capture 중91회였다.

종료 상태의 서비스도 약29%의 CPU를 사용하므로 이 부하를 줄이는 것이 우선적인 개선 후보다. 여섯 참가팀 정책도 CPU를 크게 사용한다. GPU를 연결해 기존 TinyRenderer 코드를 그대로 실행하는 것으로는 해결되지 않으며, EGL 등 GPU 렌더링 경로를 도입해 영상 지연을 비교해야 한다. CPU 사용 비중만으로 GPU 전환 후 FPS나 주행 성능을 보장할 수는 없다.

이번 결과는 기존 서비스를 함께 실행한 한 번의 짧은 표본이다. 실제 경기 하나만 실행할 때의 부하나 장시간·다른 배치의 결과와 동일하다고 보장하지 않는다.
