# Codex Cloud와 Oracle 운영 서버 비교

2026-11-12 UTC. [원시 수치](codex-cloud-comparison-20261112.json), [Oracle 기준 측정](oracle-resources-43230291498.md).

Codex Cloud의4코어 예산을 사용한 실행에서는 새 영상1장 렌더링 지연 중앙값이0.884초에서0.361초로 약59% 줄었다. 종료 상태의 대기 서비스를 함께 실행하지 않은4코어 단독 실행은0.272초로 약69% 줄었다. 같은2코어 예산으로 제한한 Codex는 이번 실행에서 Oracle보다 느렸다. 플랫폼 변경 자체보다는 CPU 예산 확대의 효과를 확인한 결과로 해석하는 것이 적절하다.

## 조건과 결과

공통 조건은 같은 애플리케이션 소스(`299c9b3`)·의존성 lock·seed20261107·`smoke_six`·6팀 `baseline`·시험용 `FixtureLLM`·CPU TinyRenderer·로봇 카메라640×480이다. 준비 완료 후 각60초간 실제 HTTP 서버와 참가팀 프로세스 여섯 개를 실행했다. cProfile은 끄고 약1초 간격으로 자원을 계측했다. GPU는 사용하지 않았다.

Codex 환경은 CPU quota4코어 상당·RAM32GiB이며 Xeon Platinum8573C x86_64를 사용했다. CPU affinity는2개 또는4개로 제한했고 모든 자식 프로세스가 같은 affinity를 상속했다. 위 CPU 수치는 테스트 프로세스 트리의 사용 시간 합계다. Codex의 cgroup 메모리·CPU 카운터는 전체 개발환경과 대기 서비스까지 포함하므로 Oracle의 테스트 전용 컨테이너 수치와 같은 범위로 비교하면 안 된다.

## 재현과 해석의 범위

기본 실행 명령은 다음과 같고2코어 조건에서는 `--cpus 2`를 사용했다. 각 실행에는 새 출력 디렉터리를 지정했다.

```bash
.venv/bin/python scripts/profile_realtime_cpu.py \
  --policy baseline --cpus 4 --seconds 60 --no-profile --sample-resources \
  --out artifacts/new-codex-comparison
```

대기 부하가 있는 Codex 조건에서는 같은 코어 affinity에서 별도 웹 서버·경기 코어·비동기 렌더러를 `finished` 상태로 실행했다. 첫 장면 렌더링을 위해5초 대기한 뒤 테스트를 시작했다. Oracle의 실제 종료 서비스와 장면·스케줄링·우선순위가 완전히 같지는 않다. Oracle은 Python3.10.12·ARM64이고 Codex는 Python3.10.22·x86_64라 패키지 바이너리도 다르다.

조건당 한 번의60초 표본이다. 실시간 스케줄링과 영상 수신 시각에 따라 정책의 이동·캐시 재사용 비율도 달라진다. Oracle은130회 capture 중91회가 동일 장면 캐시였고 Codex4코어 단독은139회 모두 새 렌더였다. 캐시를 포함한 capture 중앙값으로 새 영상 렌더링 성능을 비교하지 않았다. 브라우저 FPS·외부 접속 지연·전체 임무 성공률은 이번 측정에 포함되지 않는다.

Codex Cloud에서 개발·리허설 실행은 가능하지만, 세션 종료나 환경 재시작 뒤 실행이 유지되는 상시 호스팅을 이 결과가 보장하지 않는다. 서비스 이전을 결정하기 전에 이 운영 차이를 고려해야 한다. 실제 Oracle 서비스·DNS·비밀번호는 이번 실험에서 변경하지 않았다.
