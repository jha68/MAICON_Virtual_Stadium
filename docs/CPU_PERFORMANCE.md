# CPU 병목 측정과 최적화

2026-11-12, 로컬 Xeon8573C·Python3.10.22에서 서버와 여섯 참가팀 프로세스의 CPU affinity를2개로 제한했다. 실제 HTTP·100Hz 코어·PyBullet TinyRenderer·640×480 카메라·순찰 정책을 실행했다. 각 표본은 준비 완료 뒤20초이며 성능 수치는 cProfile 없이 측정했다.

| 구성 | 실제 경과 | 경기 시간 진행 | 실시간 배율 | 코어 tick 중앙값 |
|---|---:|---:|---:|---:|
| 변경 전 |20.03초|8.84초|0.44×|2.68ms|
| 렌더 상태 복사 최적화 |20.02초|19.97초|1.00×|0.22ms|
| 순찰의 불필요한 영상 인식도 제거 |20.11초|17.28초|0.86×|0.25ms|

마지막 구성은 변경 전보다 이 짧은 표본에서 약1.95배의 경기 시간을 진행했다. 각 실행의 로봇 이동·스케줄링은 달라지므로 구성별 수치를 정밀한 순위나 보장값으로 해석하지 않는다. 운영 서버는 ARM·2OCPU이므로 별도 실측이 필요하다. 원시 수치는 [측정 기록](evidence/cpu-optimization-20261112.json)에 있다.

## 변경 내용

- 센서 갱신마다 점수·보고서·주행 명령까지 포함한 전체 엔진 snapshot을 만들던 경로를 제거했다. 렌더러에는 분리 복사한 위치·외형 상태만 보낸다.
- headless 렌더러의 장면 전달은 실제 카메라·드론 캡처 tick에 수행한다. 카메라10Hz·드론1Hz 요청, LiDAR·odom 등 센서 생성 주기는 유지한다. GUI 관찰자는 모든 갱신을 계속 받는다.
- 순찰·blocker·capture_runner에서 사용하지 않는 RGB 검출기를 실행하지 않는다. baseline의 영상 인식·공격·보고 흐름은 그대로 실행한다.

CPU 카메라 렌더링은 계속 병목이다. 이번 측정의 렌더 중앙 지연은 약0.5초였고 요청된 모든 카메라 프레임을 생성하지 못했다. 경기 시간 진행 개선과 카메라 FPS 개선을 구분해야 한다. GPU를 사용하려면 별도 EGL 렌더링 경로를 구현·실측해야 하며, 현재 배포는 GPU를 사용하지 않는다.

## 재측정

같은 코드를 설치한 Linux 환경에서 저장소 루트의 새 출력 디렉터리를 지정한다. 기존 출력은 덮어쓰지 않는다.

```bash
.venv/bin/python scripts/profile_realtime_cpu.py \
  --policy patrol --cpus 2 --seconds 20 --no-profile \
  --out artifacts/cpu-measurement-new
```

`--no-profile`을 빼면 코어·렌더 프로세스·참가팀 메인 루프의 cProfile 파일도 저장한다. 프로파일러 자체가 실행 속도에 영향을 준다. 참가팀의 별도 추론·계획 스레드 전체를 계측하는 기능은 아니다. `--policy baseline`은 실제 기본 자율 정책 비교에 사용한다. 출력에는 운영 서버 비밀번호나 외부 LLM 키를 사용하지 않는다.
